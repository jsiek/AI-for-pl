# Spec templates for sglib (plan Q12)

sglib is generic through macros: `SGLIB_DEFINE_DL_LIST_FUNCTIONS(type,
comparator, previous, next)` expands to the list functions for one node
type and two link fields.  `sglib_dl_list_spec.h` does the same for B1's
ACSL: its macros take the same parameters and expand to the predicates,
the public contracts and the proof annotations.  Each instantiation is
still expanded and proved on its own; the template only removes the
need to rewrite the spec by hand for a new one.

## Does Frama-C expand macros inside annotations?

Yes, in every position B1 needs.  Frama-C 33 preprocesses annotations
(`-pp-annot`, on by default with gcc's cpp), so a macro used inside
`/*@ ... */` is expanded before the ACSL is parsed (the liveness model's
`/*@ ARIADNE_ALLOC */` already relied on this).  Checked on a probe file
and then on B1:

| Position | Works | Note |
|----------|-------|------|
| file-scope logic block (predicates, inductive, lemmas) | yes | several declarations per macro |
| function contract | yes | |
| assert inside a function body | yes | **one assert per comment**: a macro that expands to two asserts in one comment is refused ("Only one code annotation is allowed per comment"), so each assert is its own macro |
| loop annotation (invariants + `loop assigns`) | yes | one macro for the whole loop annotation |

The functions are generated by sglib's macros, and a macro cannot put a
comment (an annotation) into the code it generates.  So, as before (plan
Q4), the annotated file holds sglib's *expanded* code (`gen.sh`), and the
annotations in it are template invocations, written next to the code
they annotate.  WP and RTE place the expanded clauses at the line of the
invocation.

## Instantiating

```c
#include "ariadne_alloc.h"
#include "sglib_dl_list_spec.h"      /* -I/ariadne/bench/sglib_spec */

/*@ SGLIB_DL_LIST_SPEC(dllist, ptr_to_previous, ptr_to_next)
    SGLIB_DL_LIST_LEMMAS(dllist, ptr_to_previous, ptr_to_next) */

/*@ SGLIB_DL_LIST_CONTRACT_ADD(dllist, ptr_to_previous, ptr_to_next, i) */
void sglib_dllist_add(dllist **list, dllist *elem) { ...
    /*@ SGLIB_DL_LIST_ANNOT_ADD_FRAME(dllist, ptr_to_previous, ptr_to_next) */
```

`../b1/b1.c` is the full instantiation (B1: `dllist`, `ptr_to_previous`,
`ptr_to_next`); `../b1/b1_frozen.c` uses only the public macros.

| Macro | What | Public (Q11)? |
|-------|------|---------------|
| `SGLIB_DL_LIST_SPEC` | predicates `live`, `mem`, `all_live`, `all_init`, `dll`, `unchanged`, `live_dll`, `in_live_list`, `iter_ok` | yes |
| `SGLIB_DL_LIST_CONTRACT_{ADD, GET_FIRST, GET_LAST, IT_INIT_ON_EQUAL, IT_INIT, IT_NEXT}` | the contracts of the seven verified functions (B1's driver `b1` has its own) | yes |
| `SGLIB_DL_LIST_LEMMAS` | the eleven lemmas, in B1's order | no |
| `SGLIB_DL_LIST_ANNOT_*` | the asserts and loop annotations inside those functions | no |

### Not in sglib's parameters

- **The payload field.**  `add` requires `elem_init:
  \initialized(&elem->i)`: the client must initialise the data before
  adding the node, so that later reads of it are proved.  The field name
  `i` is B1's, and sglib's macro has no parameter for it, so
  `SGLIB_DL_LIST_CONTRACT_ADD` takes a fourth argument, `payload`.  (A
  generic form, "every field but the links", is not expressible in ACSL
  without naming the fields.)
- **The comparator** is not a parameter: no annotation mentions it,
  because none of the verified functions calls it (it is used by
  `find_member`, `add_if_not_member`, `delete_if_member` and `sort`).
  When those are verified, its contract (Q12) joins the public spec.
- **Names.**  Predicate and lemma names do not depend on the
  parameters, so one translation unit holds one instantiation.  The
  iterator type is `struct sglib_<type>_iterator`, built with `##` as
  sglib does.

## Textual tools see the expansion

The guardrails (spec hashes, ACSL and ghost lints) and the RAC pipeline
read annotations as text.  They now run on the source with the macros
inside its annotations expanded by the image's cpp
(`../../harness/acsl_expand.py`): each expanded annotation is one line,
padded with the original's newlines, so line numbers do not move.  So
the frozen-spec hashes cover the ACSL that Frama-C reads, not the
invocation text, and a `#define` added to the C code that changes a
predicate is caught.  The harness also hashes this directory and
`plugin/share` before and after a run (`benchmark_untouched`).

## B1 from the template

The expansion is token for token the ACSL of the hand-written b1.c
(commit 3ba8421c and before): every predicate, contract, lemma and
in-body annotation has the same comment-free, whitespace-normalised
text (`guardrails.spec_items` and the in-body annotation list compared).
WP produces the same 321 goals with the same names, and its cache
reused the SMT results; see `../b1/README.md` for the numbers.
